# 小程序端交付验收清单（强制）

> 适用范围：**所有** `miniprogram/` 下的改动。
> 依据：本轮 PRD `Q9` 的用户裁决 —— 小程序端改动的验收，工具编译 + 真机确认是必要环节。
> 本清单是**硬要求**，不是建议；任一条未完成即视为该任务未交付。

---

## 1. 三条硬要求

### (a) 所有小程序端改动必须在微信开发者工具编译预览确认

`miniprogram/` 的任何改动，都必须在**微信开发者工具**中完成一次完整的「编译 + 预览」：

- 编译必须**零报错**；出现 warning 需逐条确认是否与本次改动相关。
- 必须打开本次改动涉及的页面，确认渲染正常、无白屏、无 `undefined` 文案。
- 仅执行 `node --test`、`node --check` 或阅读源码**不构成**本条要求的完成。

### (b) 核心链路（下单 → 支付 → 订单 → 售后）必须真机走通

核心业务链路必须在**真机**（非仅模拟器）上完整走通一遍：

1. 商品/套餐下单
2. 发起支付并完成支付结果回跳
3. 订单页可见该订单、状态正确
4. 发起售后并可在订单/售后页看到对应记录

链路中任意一环在真机上表现异常，该任务不得标记为已完成。

### (c) 不接受仅凭静态断言判定通过

> **「小程序端改动的验收，工具编译 + 真机确认是必要环节，不接受仅凭静态断言判定通过。」**

- 单元测试（含 `test/miniapp.test.js` 的静态断言、`test/miniapp-runtime.test.js` 的运行时断言）**只能作为补充**，不能替代工具编译与真机确认。
- 测试全绿**不等于**交付通过；测试全绿只是允许进入工具编译 + 真机确认的前置条件。
- 禁止以「断言通过」为由跳过 (a)、(b) 两项。

## 3. 验收记录要求

每个涉及 `miniprogram/` 的任务，完成时需在交付说明中记录：

- 微信开发者工具版本与基础库版本
- 编译结果（是否零报错）
- 真机机型与系统版本
- 上述清单中实际验证的条目编号及结论
- 未能验证的条目及其原因（未验证条目必须显式列出，不得默认通过）

---

## 4. 自动化测试的定位（明确边界）

| 手段 | 能力 | 局限 |
| --- | --- | --- |
| `test/miniapp.test.js`（静态断言） | 守住源码层面的约定：文件存在、关键字符串、结构配平、跳转目标不与 tabBar 冲突 | **无法**发现交互逻辑错误；「点了没反应」这类 bug 它看不见 |
| `test/miniapp-runtime.test.js`（运行时断言，本轮新增） | 用 `wx` 全局桩真实调用 `utils/navigation.js`、`lib/cloud-request.js`，覆盖成功/失败双路径 | 只覆盖**不依赖页面生命周期**的模块；`Page()` / `Component()` / `getApp()` 相关逻辑无法在 Node 中加载 |
| 微信开发者工具编译预览 | 捕获 WXML/WXSS 结构问题、页面注册缺失、编译期错误 | 不覆盖真机行为差异 |
| 真机走查 | 唯一能确认用户可见行为的环节 | 成本高，需人工执行 |

**结论**：自动化测试负责「快速回归 + 守住约定」，工具编译与真机走查负责「确认用户可见行为」。二者不可互相替代。
